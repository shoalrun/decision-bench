**30 October 2026 · Updated 31 October 2026**

Liquid d1.1 was added in separate measurement batches. The original four models’ measurements are retained; the addition uses the same frozen cases and matching requests.

**This evaluation tests source-code behavior, not documentation search or question answering.** Models predict what eight supplied Shoalrun functions do with concrete inputs. We execute the frozen code to establish the correct answers. Models receive code or written rules (plain-English descriptions of the code’s behavior) directly; they have no repository or documentation-site access.

Mammoth had the highest test accuracy in both the source-only and written-rules comparisons. Liquid was a lower-cost alternative: it matched Mammoth on query decomposition and, with written rules, reader defaults. Joey was cheapest, but its yes/no decisions were weak at the fixed cutoff: a “yes” probability of at least 50% means “yes”; anything lower means “no”.

## Evaluation setup

Five fixed model releases answered **496 unique cases across eight functions**: 96 retrieval-configuration cases and 400 synonym/reader-filter cases. Reader filters are page attributes, such as audience or product, used to narrow the documentation shown to a reader. Each dataset was divided equally into development and test sets. Development cases check the evaluation’s prompts and runner settings; test cases measure performance after those choices are fixed. Neither set trains the models.

In the source-only comparison, models received source code as their rules; expected answers came from executing that code. All five releases were evaluated through OpenRouter. All **2,480 source-only responses** and **6,000 presentation-comparison responses** passed format checks. The 22 preliminary Liquid calls are excluded. The shared [methodology](doc:guide.methodology) defines verification, scoring, and metrics.

The original four models ran in interleaved Python batches. Liquid used separate sequential curl batches on 30–31 October, with the same requests and a separately recorded order. **Liquid’s timings are curl transfer times, which can reuse connections and exclude Python response processing. They are not directly comparable with the other models’ round trips**, so these results do not establish a speed ranking.

`noul` questions ask yes/no and return a probability of “yes”; this runner uses a 0.5 cutoff. `choice` questions select one of four named options. The 496 unique cases contain **288 `noul` and 208 `choice`** questions.

### Reading the task results

**Liquid and Jev are promising for query decomposition:** each matched Mammoth at 40/40 on the source-only test. Liquid reported $0.0215 per 1,000 calls, compared with $0.0563 for Jev and $0.1104 for Mammoth. These 40 cases come from five related input families: groups of cases that vary the same underlying rule.

**Simple checks have cheaper options:** Liquid, Elephant, and Mammoth each scored 24/24 in the low-complexity bucket. This is a small sample from three families, rather than a deployment guarantee. Liquid scored 180/200 overall, below Mammoth’s 187/200; its development score was 196/200. The difference reinforces the need for test cases after checking the evaluation setup.

**No reliable Joey niche is established here.** It chose “no” on all 120 balanced source-only binary test cases, scoring 50%. Its 66.7% in the simple bucket equals an always-no baseline; it scored 30/80 on four-choice tasks. Probability calibration could be studied separately, but these default decisions do not establish reliable task discrimination.

## Reference format changes the result

A matched comparison supplied each of the 400 synonym/reader cases with one of three references. The reference is the material the model reads to determine how the function behaves:

- **Full source:** the entire frozen TypeScript module, including unrelated functions and type declarations.
- **Focused code:** only the relevant function and the helpers it needs, with TypeScript type annotations removed. Executing this JavaScript produced the same outcomes as the full source on all 400 cases.
- **Written rules:** a plain-English description of the function’s behavior, including relevant edge cases and error conditions, supplied instead of code. These function-level descriptions were authored and reviewed against the frozen source and reused across the function’s cases.

For example, part of the actual written contract for reader defaults says:

> Explicit lists replace default lists for the same facet. Remove all entries whose list length is zero; do not restore a default after an empty explicit list removes it.

Here, a facet is a filter category such as audience or product. The [full written contracts](https://github.com/shoalrun/decision-bench/blob/main/analysis/presentation-rules-v1.json) are available in the repository. **The correct answers still came from executing the frozen source. The written rules were input to the evaluated model, not an answer key or a judge.**

Questions, inputs, choices, and known answers stayed fixed. Requests using the three formats were mixed in a fixed order within each run. The table shows the same 200 test cases per format (120 `noul`, 80 `choice`); these are repeated views, not 600 independent questions.

| Model | Full source | Focused code | Written rules | Rules median | Rules cost per 1,000 calls |
|---|---:|---:|---:|---:|---:|
| Mammoth | 185/200 | 188/200 | 192/200 (96.0%) | 319 ms | $0.0640 |
| Liquid | 176/200 | 179/200 | 183/200 (91.5%) | 124 ms (curl) | $0.0125 |
| Jev | 164/200 | 160/200 | 180/200 (90.0%) | 221 ms | $0.0382 |
| Elephant | 154/200 | 155/200 | 180/200 (90.0%) | 248 ms | $0.0224 |
| Joey | 93/200 | 90/200 | 97/200 (48.5%) | 242 ms | $0.0064 |

Relative to full source, written rules corrected 32 Elephant answers while breaking six; Jev improved 18 and regressed two; Mammoth improved seven with no regressions. The net gains were 13, eight, and 3.5 percentage points. Development results also favored rules for these three models. Liquid improved 13 and regressed six on test, for a net gain of seven cases (3.5 percentage points); its development full-source and written-rule scores were both 195/200. Joey improved 14 and regressed ten on test, but fell from 83/200 to 80/200 on development, so its small test gain is not a consistent improvement.

**Liquid and Elephant plus explicit rules are worth testing on tasks with fixed inputs, rules, and output choices.** Both matched Mammoth at 40/40 on query decomposition and reader defaults. Across the whole test set Elephant used about 65% less reported cost than Mammoth with rules, but still made 20 errors versus Mammoth’s eight. Jev tied Elephant overall and had a lower median round trip, at higher reported cost. These are workload-specific tradeoffs, not a universal rule for choosing which model handles each task. Liquid’s rules condition scored 183/200 versus Mammoth’s 192/200, at about 80% lower reported usage cost. It was task-sensitive: rules raised reader defaults from 32/40 to 40/40 but reduced phrase matching from 30/40 to 25/40.

Written rules also helped beyond the simple bucket: Elephant scored 68/72 on the high-complexity cases, compared with 55/72 using full source. Mammoth scored 72/72 with rules; Jev scored 64/72. Joey’s rules result still favored “no” on 105 of 120 binary questions, whose known answers are evenly balanced.

Shortening source alone did not consistently improve accuracy. Focused code and written rules generally used fewer input tokens (the provider’s units of text), but rules also made runtime details more explicit. Similar average token counts for focused code and rules do not isolate language or context length as the cause of the score changes; exact token measurements remain in the aggregate results.

## Questions and limits

The [retrieval development](doc:reference.questions-dev), [retrieval test](doc:reference.questions-test), and [synonym/reader-filter catalog](doc:reference.expanded-cases) list every concrete question, input, choice, and known answer. They cover acceptance, phrase matching, provider selection, and exact returned outcomes.

These are synthetic code-tracing tasks—predicting what supplied code does—with shared templates, not hundreds of independent observations or a general model ranking. Some cases depend on JavaScript quirks: in the source-only comparison, all five models rejected inherited option-property names (names available through JavaScript’s object prototype) that the actual validator accepts. Mammoth was nearly certain on four such wrong answers, so confidence alone is an unreliable guard.

The presentation study reuses observed cases and is not fresh blind generalization. Focused-code equivalence was checked by execution on all 400 inputs; written-rule fidelity was reviewed against source, not proved by executing prose. The source-only and presentation-study full-source conditions use the same source text but different instructions and passage IDs; they are not identical-prompt repeatability runs. Format comparisons use the matched conditions within the presentation study. Before adopting a routing policy (a rule for choosing which model handles each task), test it on fresh cases representative of the intended workload.

## Reproduction

All scored comparisons used request-order seed 42 and a 30-second timeout, with no inference retries. Curl’s user configuration was disabled for Liquid. The [run guide](doc:guide.run) lists dataset sizes and request caps.

The fixtures are `data/shoalrun-known-v1.json`, `data/shoalrun-expanded-v1.json`, and `data/shoalrun-presentations-v1.json`; the model configurations are `models/expanded-2026-10-30.json` for the original four and `models/liquid-2026-10-30.json` for Liquid. Resolved releases were `baseten/mammoth-1-20261021`, `typesafe/jev-1.14-20261014`, `baseten/elephant-1-20261021`, `baseten/joey-1-20261029`, and `liquid/d1.1-20261027`.
